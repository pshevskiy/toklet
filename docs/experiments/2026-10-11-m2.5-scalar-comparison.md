# M2.5 scalar reference qualification and external comparison

M2.5's profiling and benchmark requirements are covered by the accepted scalar
reference records: all eight workloads, real 2,048-position commit/rejection,
separate loading/conversion and request components, sustained requests, and the
full application trace. The controlled external matrix is available on the
same Apple M1 Pro. This establishes timing boundaries and reference behavior;
it does not retain the opt-in tiled optimization or qualify a full GPU engine.
Astra accepted the consolidated evidence and scope without findings; M2.5 is
complete.

All rows use the pinned Qwen2.5-0.5B-Instruct source, prepared token IDs, FP32
weight/KV storage, 128 fixed teacher-forced output IDs and capacity 2,048.
Each row retains three warmups and ten measured requests, with median and
dispersion in its linked record. Times below are seconds. Native CPU request
timers exclude sampling, tokenization, detokenization, JSON transport, admission
and event-buffer allocation; external records use completed engine work.
These are separate runs under each record's retained conditions, not one

The [external matrix](../../benchmarks/results/2026-10-10-external-matrix.md)
links every raw llama.cpp/MLX record, TTFT/decode summaries and native state
checks. MLX supplies the four empty-session prompt lengths; no matching MLX

prefill rate, state/events, memory, exact worker/driver identities and conditions.
The separate [paired primary CPU comparison](2026-10-10-cpu-primary-comparison.md)
uses a qualified common executable, reverses scalar/tiled order and confirms
its primary improvement in a second run. It is M3 candidate evidence, not a
replacement for the historical scalar matrix's recorded worker identities.

Append prepares 512 tokens outside timing and evaluates only 64 appended IDs.
Fully cached requests evaluate zero prompt tokens; pending requests evaluate
one fixed pending-sample stand-in. Changed histories reuse zero positions and
replay all 512. Ordinary requests commit prompt plus 127 output positions and
leave the final output pending. The separate boundary verification commits the
final pending token to reach 2,048 and rejects one more before mutation.
Fully cached sub-microsecond TTFT accesses the completed distribution and stages
a fixed ID; it is not sampling, visible latency or qualified timer precision.
Decode uses 127 completed inter-token intervals.

## Representation, memory and measured gap

The scalar reference uses FP32 storage with FP64 projection accumulation.
MLX converts floating weights once and checks actual FP32 KV. The pinned M1
llama.cpp GEMM uses Half operands despite FP32 weight storage; small-batch
numerical probes do not qualify its larger GEMM or held-out quality. Matching
checkpoint/storage/tokens supports this scoped timing comparison but does not
establish equivalent arithmetic or an external quality ranking. The records
show a substantial CPU latency gap; M2.5 explicitly permits a slow reference.

Scalar matrix physical peaks are approximately 2.044 GB and remain below
6 GiB. The application peak is 2,128,758,896 bytes with 2,353,012,560-byte
admission including tokenizer/application allowances. The MLX matrix reports
3,342,387,216 to 3,799,270,672-byte own-process peaks under its allocation policy.
llama.cpp's kernel charge counter omits clean mapped weights, so its complete
mapped/shared physical peak is unavailable. Its 5,088,231,424-byte conservative
admission is an estimate, not a measured peak. No total-memory ranking follows.

All reports name MacBookPro18,3 / Apple M1 Pro / 16 GiB / macOS 26.6.2 (25G83)
and retain individual source revisions, compiler/flags, model/tokenizer hashes,
power and endpoint thermal observations. Energy, continuous temperature,
system pressure and isolated external compilation/scratch remain unavailable
where recorded. Source hashing warms files before loading, so new-process
startup is not cold-storage qualification. No reliable tail percentile is
inferred from ten requests.

## Application, startup and sustained coverage

The [full scalar application trace](2026-10-11-application-scalar.md) retains
three warmups and ten uninterrupted measured three-turn scenarios, with
263.230241-second median scenario latency (260.727219–266.067983-second range).
All thirty measured turns reproduce their prompt's token IDs, visible text,
stops and committed/pending state. Submission-to-first-visible-text medians
are 11.606069, 24.114077 and 36.922609 seconds; finalized response medians are
100.282415, 36.626189 and 125.966325 seconds. Their medians must not be summed
to construct the scenario median.

New-process submission-to-ready is recorded separately at 2.063503 seconds:
native model load 1.902842 seconds including 1.179785 seconds of conversion,
plus tokenizer load 0.121991 seconds. Native numerical, sampling, formatting/
tokenization, detokenization and publication components overlap native totals
and are separately retained. The driver timestamps include transport and
complete JSON-line receipt; finalized response includes reset/Unicode suffix.
Later turns use scripted assistant history, with empty KV per turn and resident
weights/buffers. This is not live tool execution, task scoring or an external
application-speed comparison.

The short scalar record contains more than 21 minutes of measured requests
with resets; the fresh changed-prefix and full application records also contain
uninterrupted sequences exceeding ten minutes. Their power/thermal observations
and raw samples establish the required documented sustained sequence scope.
An excluded first short warmup was paused for an external baseline; measured
short requests completed with other performance jobs stopped, while small
source/tooling work continued as documented. Inter-workload orchestration holds
prevent claiming the entire historical matrix was one continuous run. Later
fresh changed-prefix/application runs keep checks, builds, native workloads and
large hashes outside numerical execution.

## Correctness, quality and milestone scope

The accepted [real session qualification](../../benchmarks/results/2026-10-09-qwen-session.md)
and [CLI qualification](../../benchmarks/results/2026-10-10-qwen-cli.md)
retain independent numerical, cache/pending, chat/tokenizer and recovery checks.
The actual scalar boundary measurement establishes full capacity execution and
pre-mutation rejection beyond it. Existing checked code is referenced rather
than rebuilt for this documentation task.

The [10,000-target loss comparison](2026-10-11-held-out-tiled-loss.md) has
scalar mean NLL 2.883725149929484 and identical scalar/tiled full-logit hashes
and NLL events, with zero increase against the unchanged 0.05-nats/token gate.
The [100-task comparison](2026-10-11-held-out-task-quality.md) resolves both
modes at 2/100 with exact response/outcome equality and zero drop against the
unchanged two-percentage-point gate. Code remains 0/40, prose 1/30 and
continuation 1/30 under literal frozen scoring. No repair, gate relaxation or
general capability claim is made.

M2.5's completion does not adopt tiled defaults. M3.1 still needs seven
non-short tiled workload measurements, full tiled application evidence and an
explicit retention decision. Full GPU model execution, Q4, external quality/
total-memory ranking and physical iPhone qualification remain separate work.
Astra verified the table against the accepted reports, checked all report links
and accepted M2.5 closure without findings. Local link/content and whitespace
checks pass. No engine code, numerical helper or qualified artifact changed;
this documentation task runs no new model, benchmark or test suite.
