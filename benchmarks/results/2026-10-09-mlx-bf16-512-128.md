# M0.4 MLX baseline, 9 October 2026

[Raw samples and identity](2026-10-09-mlx-bf16-512-128.json) record ten requests
following three warmups, on Apple M1 Pro with 16 GiB, macOS 26.6.2 (25G83).
AC power was attached; AC low-power mode was disabled. `pmset` reported no
thermal/performance warning, without measuring temperature or energy.

The workload uses the pinned source Qwen/tokenizer, 512 raw input token IDs,
128 fixed teacher-forced output steps, batch one, and a fresh native MLX KV
cache for every request. Weights and KV remain BF16. The admitted limit is
2,048 positions; native allocation grows to 768 positions and the final
emitted token remains pending, with 639 tokens committed.

| Measurement | Result |
| --- | ---: |
| Warm TTFT median | 134.531 ms |
| Warm TTFT min–max | 132.578–144.855 ms |
| Prefill median | 3807.71 tokens/s |
| Decode median | 115.29 steps/s |
| Complete request median | 1.237924 s |
| Model load | 0.745746 s |
| Physical process peak | 1941932168 bytes |
| Logical weights | 988065536 bytes |
| Allocated KV | 9437184 bytes |

Decode rate counts 127 intervals from the first distribution to the last.
Each timestamp follows `mx.eval` of final-position logits and all layer cache
states. Prefill follows pinned MLX-LM generation scheduling: evaluate only KV
for all but the last prompt token, clear the allocator cache, then evaluate
the last token's distribution. Unused prefix vocabulary projections remain
unevaluated. No host wait occurs between layers. TTFT includes cache/input-array
preparation; the numerical prefill timer starts after that preparation.
Tokenization, sampling, detokenization and token readback are excluded; these
are teacher-forced events, with no visible-text latency claim.

Before model loading, source hash verification reads the weight file and can
warm the filesystem cache. Model load is therefore not a cold-storage result.
Python/module startup and isolated kernel-compilation time are not measured.
The kernel-reported physical peak includes loading, Python/tokenizer state,
warmups and requests. MLX allocation counters are separately recorded and are
not added to physical footprint. Unavailable scratch accounting, system memory
pressure and energy remain null. The reported physical peak is below the initial
6 GiB ceiling, without qualifying future engine configurations.

The record identifies the pre-task repository revision and dirty state, exact
adapter SHA-256, Python lock hash, baseline versions, model/tokenizer revisions,
artifact hashes and workload token hashes. The adapter and this record are
committed together after review. The run uses MLX-LM 0.32.0/MLX 0.32.3 native
model operations; it measures a declared token-forward path. This baseline has
no quality scores yet and is not a qualified engine comparison ranking.

Reproduce explicitly on the Mac, with the locked environment and pinned sources:

```sh
.venv/bin/python tools/bench/prepare.py --fetch
.venv/bin/python tools/bench/prepare.py --fetch-weights
.venv/bin/python tools/bench/mlx_baseline.py --output benchmarks/raw/mlx-repeat.json
```

The output path must be new. GPU access is required; ordinary Rust/contract
checks do not require it. The host has Command Line Tools selected and no
`xcrun metal` executable; native prebuilt MLX GPU execution succeeded, while
Toklet's own Metal toolchain qualification remains in M4. A llama.cpp adapter
is deferred to M2 as permitted by the plan. No speed lead is claimed.
